# Localization (gettext: .pot and .po)

All user-facing text MUST be wrapped in `i18n()` — code, comments and identifiers stay English.

The model is the opposite way round from `.resx`. There, a key is invented and every language fills
it in. Here **the English text is the string itself**, written inline at the place it is used:

```cpp
m_cancelButton->setText(i18n("Cancel"));
```

Nothing is added anywhere else. The catalogue is *derived* from that call, which is what makes the
rules below about extraction matter: a string the extractor cannot see does not exist, and nothing
reports it.

## The files

| File | Who writes it |
|---|---|
| `po/<domain>.pot` | `i18n.py extract`. **Never hand-edited.** A template, not a translation. |
| `po/<lang>/<domain>.po` | A translator, or you. The only file a `msgstr` goes into. |
| `*.mo` | The build: `ki18n_install(po)` in CMake, `rust.py install` for a crate. Never in the source tree. |

There is **no `po/en`**. English is not a translation; it is the `msgid`.

`<domain>` is `i18n.domain` in `Scripts/project.toml`, and it must be the same name the program
passes to `KLocalizedString::setApplicationDomain()`. A mismatch is silent: every string falls back
to English and nothing warns.

## The four commands

```bash
python3 Scripts/i18n.py extract          rebuild the .pot from the sources
python3 Scripts/i18n.py update [de ...]  extract, then merge it into each .po
python3 Scripts/i18n.py add fr           start a language from the current .pot
python3 Scripts/i18n.py status           translated / fuzzy / untranslated, per language
```

`update` is the one to run after touching any string. It re-extracts first, so a stale `.pot` cannot
be merged by accident; `--no-extract` opts out when that is what you want.

Re-running `extract` when nothing changed writes nothing — the timestamp alone is not a change worth
a diff. So an empty `repo.py diff` after `update` means the catalogue was already current, not that
the command failed.

## Adding a string

1. Write it in the source, in English, inside `i18n()`.
2. `python3 Scripts/i18n.py update`
3. Fill in the new `msgstr` in `po/<lang>/<domain>.po` for every language.
4. Commit the source, the `.pot` **and** every `.po`.

Leaving step 3 out is not an error anywhere: an empty `msgstr` falls back to English, so the only
thing that notices is `i18n.py status`. Run it before committing.

## Changing a string

`msgmerge` marks every translation of a changed English text **fuzzy** and keeps the old `msgid`
above it as `#| msgid`, so the translation can be corrected rather than written again:

```po
#, fuzzy
#| msgid "Cannot read the file"
msgid "Cannot read \"%1\": %2"
msgstr "Die Datei kann nicht gelesen werden"
```

**A fuzzy entry is not used at runtime.** gettext skips it and shows the English. This is the single
most common way a translation "disappears" after an edit: the `.po` looks full, `status` says
`1 fuzzy translation`, and the program is in English. Fix the text, then delete both the
`#, fuzzy` line and the `#| msgid` line.

## Removing a string

Delete the call and run `update`. The entry is kept at the bottom of each `.po`, commented out with
`#~`, in case the string comes back. That is fine to leave; `msgattrib --no-obsolete` clears them out
when they have piled up.

## Writing a translatable string

**Placeholders are `%1`, `%2` — never `printf` style, never concatenation.**

```cpp
i18n("Cannot read \"%1\": %2", fileName, file.errorString())   // yes
i18n("Cannot read: ") + fileName                               // no
```

`%1` is numbered so a translation can reorder it, which German needs constantly. Concatenation takes
that away and also hands the translator two fragments that cannot be read as a sentence.

**The argument must be a literal.** Extraction is static: `xgettext` reads the source, it does not
run it.

```cpp
i18n("Details")        // extracted
i18n(title)            // extracts nothing, translates nothing, warns about nothing
```

A string that has to be chosen at runtime is a `switch` over literal `i18n()` calls, not `i18n()`
over a variable.

**Same word, different meanings → `i18nc`.** The context is the first argument and is not shown:

```cpp
i18nc("@action:button", "Open")
i18nc("@title:window", "Open")
```

German needs this more often than English suggests — "Open" is *Öffnen* as a button and *Geöffnet*
as a state. Without a context both share one `msgid` and one translation has to be wrong.

**Plurals are `i18np`, never an `if`.**

```cpp
i18np("%1 file", "%1 files", count)     // yes
count == 1 ? i18n("1 file") : i18n(...) // no - not every language has two forms
```

**A note to the translator goes in a `// i18n:` comment** directly above the call. It is extracted
into the `.pot` and is the only way a translator learns what `%1` holds:

```cpp
// i18n: %1 is the D-Bus service name, %2 the error from the bus
err() << i18n("Cannot register \"%1\": %2", service, error);
```

## Translating into German

- Quotation marks are `„…"`, not `"…"`, including around a `%1`.
- A space before the ellipsis: `Durchsuchen …`, `Wird abgebrochen …`.
- **Literal keywords stay English.** Type names, option names, enum spellings — anything the user
  types or the program parses. Translating `text, pass, int` inside a German sentence produces a
  message that names values the program will reject.
- Metavariables that are only ever displayed *are* translated: `NAME:TYPE:Label` → `NAME:TYP:Beschriftung`, `WxH` → `BxH`.
- The program's own name gets an entry translated to itself rather than left empty. That is the KDE
  convention: it is there so a language not written in the Latin script can transliterate it.

## Wiring

C++/KDE, in the top-level `CMakeLists.txt`:

```cmake
ki18n_install(po)
```

That compiles every `.po` to a `.mo` at build time and installs it where `KLocalizedString` looks.
There is deliberately no `compile` verb in `i18n.py` — a `.mo` in the source tree is a build artefact
nobody asked for.

## Testing a language

Do not trust a clean build; it proves only that the `.po` parses. Install to a throwaway prefix and
run against it:

```bash
cmake --install build --prefix /tmp/i18ntest
XDG_DATA_DIRS=/tmp/i18ntest/share:/usr/share LANGUAGE=de /tmp/i18ntest/bin/<binary> --help
```

`LANGUAGE=de` is what selects it, and it overrides the session's locale. Check an error path too,
not just `--help` — the error strings are the ones nobody looks at.

If it comes out English: the domain does not match `setApplicationDomain()`, the entry is fuzzy, or
`XDG_DATA_DIRS` does not reach the prefix. In that order.

## Rust

Same `.pot`, same `.po`, same commands — set `flavour = "rust"` in the `[i18n]` block and `i18n.py`
runs `xgettext --language=Rust` over the `.rs` files instead. gettext 0.26 parses Rust itself and
knows gettext-rs' functions by default, so nothing has to be listed.

```rust
use gettextrs::{gettext, ngettext};        // imported, never called as gettextrs::gettext
```

**Four things differ from the C++ page above:**

1. **A qualified call extracts nothing.** `xgettext` matches on the function *name*, so
   `gettextrs::gettext("Close")` compiles, runs, and never reaches the `.pot`. Import the function.
2. **Placeholders are `{name}`, not `%1`,** and they are filled *after* the lookup — `format!` needs
   a literal and a catalogue entry arrives at runtime. Each project has a small `fill(template,
   &[("name", value)])` for it. `xgettext` marks those entries `#, rust-format`, so `msgfmt
   --check-format` (which `i18n.py status` runs) catches a translation that drops one.
3. **A `const` array of strings extracts nothing either** — same static-extraction rule as
   `i18n(variable)`. Labels that live in a table become a `match` of literal `gettext()` calls.
4. **`gettext` is bound, not found.** There is no `ki18n_install(po)` and no `setApplicationDomain`:
   `setlocale(LcAll, "")` (unsafe in gettext-rs 0.8 — call it as the first statement of `main`),
   then `bindtextdomain(domain, <prefix>/share/locale)` and `textdomain(domain)`. Derive the prefix
   from `current_exe()` rather than pinning it at build time. `rust.py install` compiles the `.po`
   files into that prefix.

`i18nc` is `pgettext(context, text)`, `i18np` is `ngettext(singular, plural, n)`.

**In a CLI tool, translate what is shown, not what is stored.** A log file, `--analyze-only` output
or anything a script greps stays English; a message that goes to both places is written twice, one
argument each. Everything on this page from *Changing a string* down applies as written.

## Checklist

1. String is a **literal** inside `i18n()`, in English.
2. Values in it are `%1`/`%2`, with a `// i18n:` comment saying what they hold.
3. Ambiguous word → `i18nc` with a context. Countable → `i18np`.
4. `python3 Scripts/i18n.py update` run.
5. Every new `msgstr` filled in, every `#, fuzzy` reviewed and cleared.
6. `python3 Scripts/i18n.py status` shows 0 fuzzy and 0 untranslated.
7. Source, `.pot` and every `.po` committed together.
